test_assets · 用例 / 计划 / 基线

模块位置：backend/app/modules/test_assets/。管的是「测什么」：用例（TestCase）、测试计划（TestPlan）、性能基线（PerfBaseline）与导入源（ImportSource）。

1. TestCase：生命周期与版本

DRAFT ──submit-review──▶ PENDING_REVIEW ──review(approve)──▶ ACTIVE
   ▲                          │
   │                     review(reject)
   └──────────── 回到 DRAFT ◀─┘        ACTIVE ──失效判定──▶ validity=invalid
  • 每次变更产生不可变 TestCaseVersion（version_seq 递增，快照含 steps/assertions/locator_health）；current_version_id 指向当前版本。
  • case_type ∈ {api, web, performance, referenced}；execution_mode ∈ {script, agent}。执行时二者必须匹配（API-062 校验）。
  • ai-generated 标签：AI 生成的用例在后端打标；ACTIVE 前置人工评审（FR-05）。
  • ai-generated 的用例被聚类修正（heal_apply）时走「审批 → 新 Version + CAS」，且回滚指针 API-039 可退回上一版本。

3. 引用型用例（referenced）与 Job 契约

引用型用例不托管脚本，只声明「目标 Job + 参数 + 采集配置 + 门禁阈值映射」，实际执行在外部 CI（Jenkins）。平台侧保存的是 Job 引用，运行结果经归一化统一为 TestRun（见 执行编排）。

4. PerfBaseline 语义

{"scenario_test_case_id": "<performance 用例>",
 "metrics_snapshot": {"p95_ms": 120.0},   // 创建后不可变
 "tolerance": {"rt": 0.2},                // RT/TPS 容忍度
 "is_active": true}                        // 同场景唯一活跃（partial unique index）
  • 创建新活跃基线时 CAS 停用旧活跃；带 expected_active_version 可做乐观锁（不符 → HT-VER-001）。
  • 压测发起走 API-062，不走基线接口；基线对比数据在 API-059 供人审，不参与门禁自动判定。

5. 可变聚合一律 CAS
